# ADR-0007: Tool-call fallback grammar and repair rules

## Status

Proposed; amended 2026-09-27 (the fence label; an empty answer on a text-protocol route), 2026-09-28 (the fence
label again, on a 20-per-arm A/B; three tries for an empty answer on a text-protocol route) and 2026-09-30 (a call
written as text on a native-tools route)

## Date

2026-09-25

## Context

Many local models call tools unreliably, or the server that hosts them does not expose native tool calling. A route
declares this with `native_tools = false`. Before this decision the loop sent native tool definitions anyway and
every run on such a route failed at its first step. A text protocol must be simple enough for small models, strict
enough that ordinary answers are never mistaken for calls, and must not weaken authorization.

## Decision

- **Grammar:** a call is a fenced block labelled `tqa_call` (since instruction version 4; see the fence label below) containing one JSON object with exactly `name` and
  `arguments` (an object). Text outside blocks is prose. Several blocks are several calls, allowed only when the
  route allows parallel calls. The instructions are fixed and versioned and appear only on these routes.
- **Repairs, all fixed:** a trailing comma; bare keys and single-quoted strings; a missing closing fence at the end
  of the reply; a `json`-labelled or unlabelled block, or a whole reply, that is exactly `{name, arguments}` and names
  a known tool. Anything else that attempts a call is a failure with a stable code (`malformed`, `unknown_tool`,
  `arguments`, `schema`, `too_many`, and on a native route `text_call`, below); JSON in an answer that names no tool is prose. A block whose arguments fail the
  tool's schema is a failure, never a partial call.
- **One retry:** the first unreadable reply in a step records `provider.retry` with reason `fallback_parse: <code>`,
  and the projection derives one fixed retry prompt from it, so resume is exact. A second unreadable reply in the
  step fails the run with the error code `fallback_parse`.
- **Same authority as native calls:** parsed calls become ordinary `tool.call` events. The permission broker, the
  prepared-action hash, approvals, budgets and compaction are unchanged; nothing in the text can approve itself.
- **Transcript:** only prose is streamed; call blocks appear as tool cards. The output budget still counts every
  generated byte.
- **The fence label** (amended 27 Sep 2026). Instruction version 2 briefly wrote `tqa_call`, on the belief that a
  server's own tool parsing took `tool_call` for its marker and dropped the block. A direct check against the server
  refuted that: with the request unchanged but `logprobs` on, or with thinking off, both labels came back intact. The
  server was dropping everything after the model's reasoning on its thinking-on path without `logprobs`, whatever the
  label. So version 3 writes `tool_call` again. The parser still reads `tqa_call` blocks the same way, so replies and
  journals from version 2 parse (CORE-U-054). A route on such a server turns thinking off in its request extras.
- **The fence label again** (amended 28 Sep 2026). The check behind version 3 rested on single samples. A proper A/B
  on the same captured text-route request, 20 replies per arm, counted replies that hold a call block: `tool_call`
  12/20 with thinking on and 2/20 with it off, `tqa_call` 17/20 and 14/20. Every reply without a block was generated
  text dropped on the server, not a wrong call. With thinking off the label matters (Fisher exact p = 0.0002). With
  thinking on no difference is shown (p = 0.16). So version 4 writes `tqa_call` again, and routes keep thinking off.
  The parser still reads `tool_call` blocks the same way, so replies and journals from version 3 parse (CORE-U-054).
  This is one request's per-step rate; E2E-FALLBACK-004 measures what it does for task completion.
- **An empty answer on a text-protocol route** (amended 27 Sep 2026; tries amended 28 Sep 2026) gets up to three tries in
  all, the step's attempt budget, each retry a visible `provider.retry` with reason `empty_response` (on 28 Sep a retry
  got 13 of 21 empty replies back). It then fails with a reason that says the server returned no text on a
  text-protocol route and that, with thinking on, a server can drop the answer after its reasoning, instead of a bare
  `empty_response` (CORE-U-055).

- **A call written as text on a native-tools route** (amended 30 Sep 2026). A native route declares its tools and
  expects native `tool_calls`, but a model sometimes writes its call into the answer instead: qwen3:4b on Ollama, with
  default settings, wrote a `write_file` call as JSON closed by `</function-call>`, and the run ended completed with no
  file written and nothing said; a direct capture the same day also saw the whole answer as one JSON object with the
  tool under `function`. A silent success must never happen. So a native-route reply that delivers no native call and
  wasn't cut at the output limit is read for the explicit call forms only: a `tqa_call` or `tool_call` block, the
  native markup (which now also reads `<function-call>` and `<function_call>` around the call's JSON), and a reply that
  is nothing but one JSON object naming a tool the run offers (under `name`, `function` or `tool`) with its arguments
  (under `arguments` or `parameters`). A `json` or unlabelled block, and JSON inside a longer answer, may be an example
  a person asked for, so on a native route they're prose, with one exception (amended 30 Sep 2026, F25,
  PROMPT-U-016: qwen2.5 wrote its call in a `json` fence and the run ended "Done" having done nothing): a closed `json`
  fence that ends the reply, with nothing but whitespace after it, whose whole content is one such call object naming
  an offered tool whose arguments validate, is a call; any other `json` fence stays the answer, never a `text_call`
  failure. A readable call whose arguments validate runs like a native
  one (it is named
  `fb-<step>-<attempt>-<n>`), and its markup is never shown: as for the text protocol, text that could begin one of
  these forms (a reply that starts with `{`, a line that is or could become a `tqa_call`, `tool_call` or `json` fence, a `<`
  that is or could become a markup tag) waits until the reply is whole, and then only the narration is streamed and
  journaled, so the transcript, its replay and the model's own history hold no call markup (amended 30 Sep 2026,
  PROMPT-U-014, CORE-U-070). Held text that turns out not to be a call, such as a long JSON answer a person asked for,
  is shown whole at the reply's end, and so is a reply cut at the output limit or one with native calls. A reply that plainly carries call markup it can't read (its
  last line closes a call, or a line starts with a call's opening tag, outside fenced blocks) is a failure with the code
  `text_call`, and so is a whole-reply object that names an offered tool but has more keys than a name and arguments,
  or arguments the tool refuses: one retry whose prompt says to call the tool through the tool interface (not a
  `tqa_call` block), and a
  second fails the run with `fallback_parse`, which the page words as an answer that couldn't be used. Markup named
  mid-sentence or shown in a fence stays prose, and so does a plain answer.

## Amendment 2026-10-02: native tools on a text route, by design

The recovery for a reply the model server swallowed (CORE-U-065, built 29 Sep) sends native tool definitions on a
`native_tools = false` route, which the context above calls the old failure. It does so only on the server's own
evidence that it parses calls natively: it withheld the reply's chunks, or the reply is empty with tokens counted.
That step is asked again once with the tools declared; once native calls come back, every later request of the run
declares them (on a Gate 5 capture before 17.0, 15 of 55 requests on `local-text`). A server that refuses declared tools
keeps the route text-only for the run. So `native_tools = false` means the text protocol is the route's protocol, not
that native tools are never sent; PRD FR-2 says so.

## Amendment 2026-10-22: the retry names the problem

The one retry's prompt was fixed per failure code, and for `malformed` it said the block "is not valid JSON". On the
model-fallback night of 20 Oct 2026 that was wrong for 13 of the 20 malformed replies, which were valid JSON
without `name`, and the `schema` sentence named neither the tool nor the field. The retry request doesn't hold the
rejected reply, so the sentence is the model's only clue, and 10 of 18 retries failed again.

- **The reason stays** `fallback_parse: <code>`, as before. `provider.retry` gains an optional `fallback_problem`: a
  closed set of kinds (no `name`, no `arguments`, not JSON, cut off or at a line and column, not an object, extra keys,
  a `name` that isn't a string, an unknown tool, an unexpected, missing or wrongly typed property, another schema
  problem, too many calls), with an `other` kind that a reader takes for any kind it doesn't know. The web does the
  same: a retry whose problem kind is newer than the page is read with the problem as `other` (WEB-U-417), so an open
  tab running the old app keeps working after an upgrade.
- **Content-free:** only names (our tools', their parameters', JSON types, and a name the model wrote only when it
  looks like an identifier of at most 32 bytes, since longer identifier-shaped text is often a credential), a
  property's place inside the arguments as names and indices (`edits[0]`), only names a schema's `properties`
  declare (a map's keys are the model's own words), positions as numbers and counts. Never a value from the reply, whose arguments can hold
  anything, secrets included; the event reaches clients.
- **The sentence** keeps its fixed opening and closing, names the problem between them, may add one sentence on how
  to fix it, and stays within 400 characters. A journal without the field gives the code's fixed sentence, so an older
  journal resumes as it did. A copied-back sentence is recognised by that shape (one line, the opening, one closing
  at its end, within the bound).
- For a schema refusal the problem comes from the tool's own schema, a missing property before an unexpected one; a
  nested one names its place ("edit_file's edits[0] needs \"new_text\""), and one whose place or sentence can't be
  written that way says the schema in general. The
  instruction version is 5, so a model-fallback result says which retry sentence it had.

## Consequences

- Routes without native tool calling work, and their success rate is measured per model (E2E-FALLBACK-004).
- The grammar and repairs are the contract; a change needs a new instruction version and tests.
- Answers that contain a code block stream up to that block and deliver the rest when the reply is complete.

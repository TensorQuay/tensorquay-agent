# Release artefacts

What a release publishes besides the images themselves, and how the release manager produces it. The release pipeline
(DEV-PLAN Phase 9 item 3) will run the same steps; until it exists they are run by hand.

## Software bills of materials (ADR-0017 point 7)
Every artefact a release names gets an SPDX 2.3 JSON document and a readable package list. Images are aggregates: each
release lists every package with its exact version and the location of its matching source.

| Artefact | `--artefact` | Named by | Read from |
|---|---|---|---|
| Gateway image | `gateway` | image ID | `docker export` of the image |
| Web image | `web` | image ID | `docker export` of the image |
| Runtime base, Workstation and Desktop images | `runtime-base`, `runtime-workstation`, `runtime-desktop` | image ID | `docker export` of the image |
| VM host image | `vmm` | image ID | `docker export` of the image |
| Built-in template rootfs | `rootfs-base`, `rootfs-workstation`, `rootfs-desktop` | the manifest's rootfs SHA-256 | the ext4 image, with `debugfs rdump` |
| Guest kernel | `kernel` | the `vmlinux` SHA-256 | the kernel build directory |

The fake model image is a test fixture and is not covered.

### What is listed
- **Debian packages:** from dpkg's status, with the source package's `snapshot.debian.org` location. The licence is the
  exact SPDX expression of a machine-readable copyright file, or `LicenseRef-debian-<package>` pointing at the
  package's own notice in the image. A licence id is never guessed.
- **Rust crates:** the `cargo tree` closure of each shipped binary for its target, without dev, build or proc-macro
  edges, with the `Cargo.lock` checksum and the crates.io tarball. The project's own crates point at the repository.
- **npm packages:** every package root under the `node_modules` directories the image ships, with its registry
  tarball.
- **Components added outside a package manager**, read from the Dockerfiles' own pins: Node.js, Go (Workstation), Firecracker (VM host), musl (linked statically from the pinned Alpine build image), the Rust standard
  library, and the project's own files.
- **The kernel:** Linux, GPL-2.0-only, with the exact kernel.org tarball and its checksum. The kernel's configuration is
  published beside its SBOM, so the binary can be rebuilt from its source.

### The completeness check
Nothing is written unless all of these pass:

| Check | Fails when |
|---|---|
| C1 | an installed Debian package is not listed, or is listed without its source; for the kernel, the build's manifest does not match the Dockerfile's pins |
| C2 | an executable or ELF file is owned by no package, npm directory or declared component |
| C3 | the listed crates or npm packages differ from what the image ships |
| C4 | the project's linked code (crates, the web app's and browser's npm packages) is outside `deny.toml` or `web/licenses.json` |
| C5 | the SPDX document is malformed: an uncontained package, a repeated id, or a `LicenseRef` without its text |
| C6 | the document names another artefact than the one read (image ID, rootfs or `vmlinux` digest) |

A new binary in an image therefore needs a package, or an entry in `tools/release/sbom_artefacts.py` with its version,
licence, source and the paths it owns.

### Producing them
Build every image at the release commit, then the template rootfs (`images/rootfs/build_rootfs.py`) and the kernel
(`images/rootfs/README.md`). Then, with `SOURCE_DATE_EPOCH` set to the release commit's time:

```sh
out=dist/<version>/sbom
python3 tools/release/sbom.py --artefact gateway --image tqa-gateway:<tag> --release <version> --out "$out"
python3 tools/release/sbom.py --artefact rootfs-base --rootfs <rootfs dir>/<image id> --release <version> --out "$out"
python3 tools/release/sbom.py --artefact kernel --kernel <kernel build dir> --release <version> --out "$out"
```

Each run writes `<artefact>.spdx.json` and `<artefact>.packages.md` and adds the artefact to `index.json`; the kernel
also writes `kernel.config` and records its source link and checksum in the index. The tool works offline: images are
read from the local engine and every source is a link, never fetched. The same inputs give byte-identical output.

The Workstation image keeps its own inventory, `/usr/share/tqa/PACKAGES.md` (and `images/runtime/PACKAGES.md`),
generated by the same library, so the two cannot disagree.

### Known vulnerabilities (release gate)
After the SBOMs are written, the gate looks up what they list and fails the release on any HIGH finding:

```sh
python3 tools/release/sbom_vulns.py --sbom "$out"
```

Crates, npm packages and the Go toolchain are looked up in OSV; Debian packages in the Debian security tracker, by
source package, in the image's own release (from its `base-files`). It writes `vulns.json` and `vulns.md` beside the
SBOMs. Levels:

| Level | Meaning | Gate |
|---|---|---|
| HIGH | A fix exists and the advisory is high or critical (its reviewed label, else its CVSS v3 score); or Debian has a security update newer than the installed package, which a rebuild at a newer apt snapshot picks up | Fails |
| MEDIUM | A fix exists at a lower or unknown severity, or Debian fixed it in a point release | Reported |
| OPEN | No fix exists; those at high or critical severity are listed for acceptance or mitigation | Reported |

Components no database covers (Node, Firecracker, the guest kernel, the Rust standard library, musl) are listed as
unchecked; check them against their own release notes. The kernel headers package alone (`linux-libc-dev`) is not a
kernel and is left out. The gate needs network access to OSV and the tracker (`--tracker` takes a saved copy); it
changes nothing in the images.

### Publication
The SBOMs, package lists, the kernel's configuration and `THIRD-PARTY-NOTICES.md` go with the release notes.
Publishing a release, including these files, needs the owner's approval.

### Tests
- REL-U-001 to REL-U-007 run in every `tools/check.sh` (gate REL-U), on fixtures without Docker or network.
- REL-I-001 and REL-I-002 need the built artefacts:

```sh
TQA_DOCKER_TESTS=1 TQA_IMAGE_TAG=<tag> TQA_FC_ROOTFS_DIR=<rootfs dir> TQA_FC_KERNEL_DIR=<kernel build dir> \
    python3 -m unittest discover -s tools/release -p 'test_images.py' -v
```

## The release pipeline
`tools/release/release.py` runs the steps of this page for one commit, locally, and publishes nothing:

```sh
TQA_DOCKER_TESTS=1 python3 tools/release/release.py --version X.Y.Z --commit <sha> [--kernel] [--candidate]
```

**Refusals, before anything is built:**
- a version that isn't `X.Y.Z` or `X.Y.Z-rc.N`;
- uncommitted changes in the checkout;
- a commit not on `main` (`--candidate` allows a dry run, which is never releasable);
- a tag `vX.Y.Z` that names another commit;
- an existing `dist/X.Y.Z/`.

**Steps,** all from a clean `git archive` export of the commit, with `SOURCE_DATE_EPOCH` set to the commit's time:
1. It builds the five images, tagged locally only. A runtime image whose protocol-revision label differs from the
   commit's `PROTOCOL_REVISION` fails.
2. It builds both template rootfs, and with `--kernel` the guest kernel. Whether a release ships the kernel binary is
   the owner's decision.
3. It writes every SBOM, with the completeness check, and runs the vulnerability gate.
4. It writes:
   - `release.json`: IDs, hashes, pins, the evaluation pages, and the tag to create;
   - `RELEASE-NOTES.md`: a skeleton with pinned versions, images by ID, the gate states, the known limits collected from
     each evaluation page, and the parts a person writes marked;
   - `SHA256SUMS`.

The work goes into `dist/.X.Y.Z.partial/` and becomes `dist/X.Y.Z/` only when every step passed. A failure leaves the
partial directory with a `FAILED` file. The template rootfs images stay in a work directory and only their manifests
enter the release. The pipeline refuses `docker push`, `docker login`, `git tag` and `git push` outright: pushing the
images, creating the tag and publishing the directory are the owner's steps. Run it through the stack queue; it builds
every image.

## Updating main
The public `main` receives one squashed commit per update: its tree is exactly a verified development commit's tree
and its parent is the current `main`. `tools/release/squash-import.py` builds it and never pushes:

```sh
python3 tools/release/squash-import.py --source <verified commit> --message-file <message> --ref refs/heads/import/main
```

Before anything is written, the tree and the message get the repository guard's checks (identity, message form,
personal data, addresses, internal references, file types and sizes) and the tree gets the secrets scanner. The
report shows the change against `main` and the push that would publish it; pushing needs the owner's approval.
`--first-import` parents the commit on `main`'s first commit instead of its tip, which replaces `main`'s history
and so needs a force-push.

### The upgrade fixture
GW-I-016 upgrades a database from the previous release: `crates/tqa-gateway/tests/fixtures/upgrade-previous-release.sql`
holds synthetic rows for every table at that release's last migration, which its first line names
(`-- level: <migration>`). `squash-import.py` refuses a tree whose fixture is at any other level than the public
`main`'s last migration, and its report has a line on the fixture: at that migration, or not checked and why (no
fixture in the tree, or no migrations on `main`). So once an update of `main` has landed, the next one starts by
moving the fixture:
1. raise the level to the migration `main` now ends with;
2. add rows for every table the update added (the test fails on a table without one), and set the columns it added
   wherever a long-lived installation would have them set;
3. remove the test's entries for tables rewritten on purpose whose migration the new level has reached (a guard test
   fails on them).
